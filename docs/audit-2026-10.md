## 0. Architecture summary / context map

**What it is.** Next.js 16 App Router monolith. React 19 client pages under `app/dashboard/*` talk to
REST-style route handlers under `app/api/*`, which talk directly to MongoDB through the native driver
(`lib/mongodb.ts` → `getDb()`). There is no service or repository layer: each route handler owns its
queries.

```
Browser (React Query)                       Server (route handlers)                     MongoDB "pretvia"
───────────────────────                     ───────────────────────                     ─────────────────
app/dashboard/page.tsx ──apiFetcher/───────▶ app/api/logs, checkins, groups, …  ──────▶ users, groups, logs,
  └ useDashboardFilters  logsFetcher        │  getSession()  (JWT cookie)               groupMemberships,
  └ useDashboardPanel                       │  canManageGroup() (coach authz)            checkins, attendance,
components/** ──raw fetch (64 sites)───────▶│  buildVisibilityFilter() (who sees logs)   comments, invites, …
app/invite/[token] ──────────────────────▶  app/api/invites/[token]/redeem
middleware.ts: only checks "JWT is valid" for /dashboard/*; all real authz is per-route.
```

**Identity.** `lib/auth.ts` signs an HS256 JWT (7 days) into the httpOnly `session` cookie. The claims
include `role` and `activeGroupId`, which go stale whenever the DB changes; most routes re-read the user.

**Roles.** `athlete`, `coach`, and `guardian` (parent). A coach is either the head coach of a group
(`groups.headCoachId`) or an assistant (`groups.coachIds`).

**The four concepts every change touches:**
1. **Membership** is stored three times: `users.groupIds` (and `activeGroupId`), the `groupMemberships`
   collection (role tags), and `groups.coachIds`. Every add or remove must write all three.
2. **Log visibility**: `"coach"` (shared) or `"private"`. Legacy docs have no `visibility` field and use
   `isGroup: true` to mean shared. The canonical read rule is `buildVisibilityFilter()` in `lib/log-filters.ts`.
3. **Active group**: most endpoints scope to `users.activeGroupId`, not to a `groupId` parameter.
4. **Streaks** (`lib/streak.ts`): a log counts against a weekly training slot if it lands within 24h after
   the slot time. Slot times are interpreted as UTC.

**Invites** are single-use tokens (`invites` collection) with four types: `athlete`, `coach`, `parent`,
and `under13_parent`. Redeeming one creates the account, joins the group, and issues a session.

## 1. Code smells & refactoring targets (top 5)

### 1.1 `app/api/invites/[token]/redeem/type-handlers.ts` (529 lines) — four copies of one workflow

**Why it's risky.** `handleAthleteInvite`, `handleCoachInvite`, `handleParentInvite`, and
`handleUnder13ParentInvite` each re-implement the same steps: validate name and password, hash, insert the
user, write membership, apply the training schedule, delete the invite, and create the session. The copies
have already drifted:
- The coach path writes a bogus `coachIds` field onto the *user* document (line 306).
- The athlete path uses `$set: { groupIds }` (a read-modify-write that loses concurrent joins), while the
  coach path uses `$addToSet`.
- None of them reuse `addUserToGroup()` in `lib/group-actions.ts`, which already does most of this.
- The route claims the invite (`findOneAndDelete`, `redeem/route.ts:54`) **before** these handlers
  validate the body, so a typo in a password permanently burns the invite link.

**Refactor.** Validate before claiming, and give membership writes one owner:

```ts
// app/api/invites/[token]/redeem/account.ts
import bcrypt from "bcryptjs"
import { ObjectId, type Db, type Document } from "mongodb"
import { applyGroupTrainingScheduleToUser } from "@/lib/group-training-schedule"
import type { TrainingSlot } from "@/types/dashboard"

export type NewAccount = { firstName: string; lastName: string; password: string }

/** Validate the "create account" part of a redeem body. Returns an error message or the clean input. */
export function parseNewAccount(body: Record<string, unknown>): NewAccount | { error: string } {
  const { firstName, lastName, password } = body
  if (typeof firstName !== "string" || typeof lastName !== "string" || typeof password !== "string"
      || !firstName.trim() || !lastName.trim()) {
    return { error: "First name, last name, and password are required" }
  }
  if (password.length < 6) return { error: "Password must be at least 6 characters" }
  return { firstName: firstName.trim(), lastName: lastName.trim(), password }
}

export async function insertInvitedUser(
  db: Db,
  email: string,
  role: "athlete" | "coach" | "guardian",
  acct: NewAccount,
  extra: Record<string, unknown> = {},
): Promise<string> {
  const { insertedId } = await db.collection("users").insertOne({
    email,
    password: await bcrypt.hash(acct.password, 12),
    displayName: `${acct.firstName} ${acct.lastName}`,
    firstName: acct.firstName,
    lastName: acct.lastName,
    role,
    activeGroupId: null,
    groupIds: [],
    profileComplete: true,
    authProvider: "email",
    emailVerified: true, // the invite token was delivered to this address
    createdAt: new Date(),
    ...extra,
  })
  return insertedId.toString()
}

/**
 * The single place that puts a user into a group. Keeps all three membership stores in sync:
 * users.groupIds/activeGroupId, groupMemberships, and (for coaches) groups.coachIds.
 */
export async function joinGroup(db: Db, userId: string, group: Document, opts: { asCoach: boolean }) {
  const groupId = group._id.toString()
  await db.collection("users").updateOne(
    { _id: new ObjectId(userId) },
    { $addToSet: { groupIds: groupId }, $set: { activeGroupId: groupId } },
  )
  await db.collection("groupMemberships").updateOne(
    { userId, groupId },
    { $setOnInsert: { userId, groupId, roleIds: [] } },
    { upsert: true },
  )
  if (opts.asCoach) {
    await db.collection("groups").updateOne({ _id: group._id }, { $addToSet: { coachIds: userId } })
  }
  const template = group.trainingScheduleTemplate as TrainingSlot[] | undefined
  if (template?.length) await applyGroupTrainingScheduleToUser(db, userId, groupId, template)
}
```

Each handler then shrinks to roughly 25 lines of type-specific policy. The athlete case looks like this:

```ts
export async function handleAthleteInvite(db: Db, invite: Document, group: Document, body: Record<string, unknown>) {
  const email = (invite.email as string).toLowerCase()
  const existing = await db.collection("users").findOne({ email })
  let userId: string
  if (existing) {
    if (existing.role !== "athlete" && existing.role !== "coach") return fail(400, "This invite is for an athlete account")
    userId = existing._id.toString()
  } else {
    const acct = parseNewAccount(body)
    if ("error" in acct) return fail(400, acct.error)
    userId = await insertInvitedUser(db, email, "athlete", acct, { dateOfBirth: body.dateOfBirth ?? null })
  }
  await joinGroup(db, userId, group, { asCoach: false })
  await linkPendingGuardians(db, email, userId)
  return finishRedeem(userId, email, "athlete", group._id.toString(), "/dashboard")
}
```

In `redeem/route.ts`, call a per-type `validate(body, invite)` **before** `findOneAndDelete`. The
existing-user session check is already done that way, so this extends the same pattern.

### 1.2 `app/invite/[token]/page.tsx` (867 lines) — four near-identical forms

**Why it's risky.** `InviteUnder13Form`, `InviteAthleteForm`, `InviteCoachForm`, and `InviteParentForm`
each hold 5–9 `useState`s and the same "log in, then redeem" logic. Concrete defects:
- The login `fetch` at lines 447, 601, and 748 has no `try/catch`. A network failure becomes an unhandled
  rejection with no feedback, and the button just stops.
- `InviteCoachForm` navigates twice. `redeem()` already calls `router.push(data.redirect)`, and the form
  pushes again (lines 613 and 626).
- `res.json()` runs before any check that the response is JSON (a 502/504 page is HTML), so it throws.

**Refactor.** Move the behavior into one hook and render one form from a field config:

```tsx
// app/invite/[token]/use-invite-actions.ts
export function useInviteActions(invite: InviteData, redeem: RedeemFn) {
  const queryClient = useQueryClient()

  const loginThenRedeem = async (password: string) => {
    try {
      const res = await fetch("/api/auth/login", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ email: invite.email, password }),
      })
      const data = await res.json().catch(() => ({}))
      if (!res.ok) return void toast.error(data.error || "Login failed")
      await queryClient.invalidateQueries({ queryKey: queryKeys.auth.session })
      await redeem({ createAccount: false, email: invite.email }) // redeem() owns navigation
    } catch {
      toast.error("Network error. Please try again.")
    }
  }

  const createThenRedeem = (fields: Record<string, string>) =>
    redeem({ createAccount: true, email: invite.email, ...fields })

  return { loginThenRedeem, createThenRedeem }
}

// One form, driven by config instead of four copies:
const FORM_CONFIG = {
  athlete: { title: "Join as athlete", fields: ["firstName", "lastName", "password", "dateOfBirth"] },
  coach:   { title: "Join as coach",   fields: ["firstName", "lastName", "password"] },
  parent:  { title: "Parent account",  fields: ["firstName", "lastName", "password"] },
} as const
```

`InviteUnder13Form` keeps its own component because its fields differ, but it uses the same hook.
Expected size: about 867 → 350 lines.

### 1.3 `app/api/logs/route.ts` (482 lines) — repeated boilerplate, rules, and gaps

**Why it's risky.**
- Each of the 4 handlers repeats rate-limit, session, and try/catch (the same block appears 11 times
  across the API).
- The legacy visibility rule (`visibility || (isGroup ? "coach" : "private")`, plus the `$or` query form)
  is hand-written 6 times in this file and 11 times repo-wide.
- The daily-limit check is duplicated in POST (lines 246–278) and PUT (lines 386–417). It uses
  server-local midnight (UTC on Vercel), and it is check-then-insert, so a double-submit gets around it.
- No input validation: `emoji` can be an object, `visibility` can be `"banana"`, `notes` and `tags` are
  unbounded, and `timestamp` can become `Invalid Date`.

**Refactor.** Three small shared modules. `zod` is already in `package.json` and currently unused.

```ts
// lib/api-handler.ts — one wrapper replaces ~60 copies of the same 15 lines
import { NextResponse } from "next/server"
import type { Db } from "mongodb"
import { getSession, type SessionPayload } from "@/lib/auth"
import { getDb } from "@/lib/mongodb"
import { apiRateLimiter, getIp } from "@/lib/rate-limit"

export class ApiError extends Error {
  constructor(public status: number, message: string) { super(message) }
}

type Ctx = { req: Request; session: SessionPayload; db: Db }

export function withApiRoute(name: string, handler: (ctx: Ctx) => Promise<Response>, opts = { rateLimit: true }) {
  return async (req: Request) => {
    try {
      if (opts.rateLimit && apiRateLimiter) {
        const { success } = await apiRateLimiter.limit(getIp(req))
        if (!success) return NextResponse.json({ error: "Too many requests" }, { status: 429 })
      }
      const session = await getSession()
      if (!session) return NextResponse.json({ error: "Unauthorized" }, { status: 401 })
      return await handler({ req, session, db: await getDb() })
    } catch (err) {
      if (err instanceof ApiError) return NextResponse.json({ error: err.message }, { status: err.status })
      console.error(`${name}:`, err)
      return NextResponse.json({ error: "Something went wrong" }, { status: 500 })
    }
  }
}

/** Parse a JSON object body; malformed JSON → 400 instead of 500. */
export async function readJson(req: Request): Promise<Record<string, unknown>> {
  const body = await req.json().catch(() => null)
  if (!body || typeof body !== "object" || Array.isArray(body)) throw new ApiError(400, "Invalid JSON body")
  return body as Record<string, unknown>
}
```

```ts
// lib/log-visibility.ts — the one definition of the legacy rule
export type LogVisibility = "coach" | "private"

/** Logs written before `visibility` existed used `isGroup: true` to mean "shared with coach". */
export function resolveVisibility(log: { visibility?: unknown; isGroup?: unknown }): LogVisibility {
  if (log.visibility === "coach" || log.visibility === "private") return log.visibility
  return log.isGroup === true ? "coach" : "private"
}

/** Mongo filter matching logs whose resolved visibility is `v` (legacy-aware). */
export function visibilityQuery(v: LogVisibility) {
  return v === "coach"
    ? { $or: [{ visibility: "coach" }, { visibility: { $exists: false }, isGroup: true }] }
    : { $or: [{ visibility: "private" }, { visibility: { $exists: false }, isGroup: { $ne: true } }] }
}
```

### 1.4 `app/dashboard/page.tsx` (352 lines) — a god component

**Why it's risky.**
- It runs 8 queries, holds group-switch state machinery, and contains a localStorage side effect.
- It passes **27 props** to `DashboardFeed` and **13** to `DashboardSidebar`. `filters` and `handlers`
  are threaded through 3 levels.
- `activeGroupId` is mirrored into local state (`useState` + `useEffect`, lines 34–37). The logs query
  key uses the local copy, while tags, members, checkins, stats, and announcements use
  `user.activeGroupId`. During a group switch the keys disagree, and that disagreement is why the
  `isGroupSwitching` + `switchingGroupIdRef` workaround exists.

**Refactor.** Data in one hook, shared values in context, and no mirrored state:

```tsx
// components/main/dashboard/use-dashboard-data.ts
export function useDashboardData(user: User | null, logsUrl: string) {
  const groupId = user?.activeGroupId ?? null            // single source of truth
  const scope = [user?.id, groupId] as const
  const logs = useInfiniteQuery({ queryKey: [...queryKeys.logs.all, "list", logsUrl, ...scope], /* … */ enabled: !!user })
  const tags = useQuery({ queryKey: [...queryKeys.tags.all, ...scope], /* … */ })
  const members = useQuery({ queryKey: [...queryKeys.members.all, ...scope], enabled: user?.role === "coach" && !!groupId, /* … */ })
  // checkins, sessions, stats, announcements …
  return { logs, tags, members /* … */ }
}

// components/main/dashboard/dashboard-context.tsx
const DashboardContext = createContext<{
  user: User; filters: Filters; handlers: FilterHandlers; panel: PanelHandlers
} | null>(null)
export const useDashboard = () => {
  const ctx = useContext(DashboardContext)
  if (!ctx) throw new Error("useDashboard must be used inside <DashboardProvider>")
  return ctx
}
```

On group switch, write the new `activeGroupId` into the session query cache with
`queryClient.setQueryData(queryKeys.auth.session, …)` before invalidating. All keys then change together,
and `isGroupSwitching`/`switchingGroupIdRef` can be deleted. `DashboardFeed` drops to about 8 props.

### 1.5 `app/api/auth/account/route.ts` — irreversible cascade, no transaction, wrong scope

**Why it's risky.** It is short, but it has the largest blast radius in the codebase. About 20 sequential
deletes run with no transaction, so a failure halfway leaves a half-deleted account. It also deletes
**every** group where the user appears in `coachIds` (lines 30–45), not just groups they own. Section 3,
S3, shows how an outsider can use this to delete someone else's group. It also leaves dangling
`groupIds`/`activeGroupId` on the remaining members, and it deletes `log_reviews` by `headCoachId` while
reviews are written with `coachId`.

**Refactor.**

```ts
const coached = await db.collection("groups")
  .find({ $or: [{ headCoachId: userId }, { coachIds: userId }] }).toArray()
const owned = coached.filter((g) => g.headCoachId?.toString() === userId)
const assisted = coached.filter((g) => g.headCoachId?.toString() !== userId)

const client = await clientPromise
const s = client.startSession()
try {
  await s.withTransaction(async () => {
    for (const g of owned) await deleteGroupCascade(db, g, s)   // also $pull groupIds / unset activeGroupId on members
    if (assisted.length) {
      await db.collection("groups").updateMany(
        { _id: { $in: assisted.map((g) => g._id) } }, { $pull: { coachIds: userId } }, { session: s })
    }
    await db.collection("log_reviews").deleteMany(
      { $or: [{ coachId: userId }, { headCoachId: userId }, { logId: { $in: logIds } }] }, { session: s })
    // … remaining per-user deletes, each with { session: s }
  })
} finally {
  await s.endSession()
}
```

Atlas clusters are replica sets, so transactions are available.

## 3. Security & secrets audit

**Secrets scan: clean.** No hardcoded API keys, tokens or connection strings in tracked files.
`.env.example` contains placeholders only. `tsconfig.tsbuildinfo` is committed; that is harmless but
should be gitignored. **XSS: no exploitable sink found.** React escapes output, the only
`dangerouslySetInnerHTML` uses are static (theme script, JSON-LD), and the email templates escape user
values (`escapeHtml` in `lib/resend.ts`). **SQL injection is N/A** (MongoDB), but its NoSQL equivalent,
operator injection, is present. Ranked:

### Critical — fix first

**S1. Password-reset NoSQL injection → takeover of a chosen victim's account (new).**
`app/api/auth/reset-password/route.ts:7,26` passes the JSON body's `token` straight into
`findOne({ token })`. Sending `{"token": {"$ne": null}, "password": "attacker1"}` matches *some* reset
token. The handler then sets that account's password and marks it verified. An attacker first calls
`/api/auth/forgot-password` for the victim's email to plant a token, then repeats the request. Each call
consumes (deletes) or uses the first matching token, until the victim's token is reached. This endpoint
has no rate limit.
*Fix (5 lines):*

```ts
const { token, password } = await readJson(req)
if (typeof token !== "string" || !/^[0-9a-f-]{36}$/i.test(token) || typeof password !== "string") {
  return NextResponse.json({ error: "Invalid or expired reset link." }, { status: 400 })
}
// and: atomically claim with findOneAndDelete({ token }), add passwordResetRateLimiter
```

Follow-up hardening: store only a SHA-256 of the token, and add a TTL index.

**S2. Signup NoSQL injection bypasses the coach waitlist (new).**
`app/api/auth/signup/route.ts` reads `waitlistToken` and `coachInviteToken` from the body and queries
`findOne({ inviteToken: waitlistToken, status: "approved" })` (line 92; same for `coachInviteToken` at line 73). Passing
`{"$ne": null}` (or `$regex` variants to walk through entries) matches someone else's approved entry and
creates a **coach** account without approval. That account is the starting point for S3.
*Fix:* `typeof waitlistToken === "string"` and `typeof coachInviteToken === "string"` guards, or a zod
schema for the whole body.

**S3. A group's join code works as a co-coach key; chained with account deletion it destroys a group (new).**
- The 6-character join code is returned to **every member, athletes included**
  (`GET /api/groups?mode=my-groups`, `app/api/groups/route.ts:103`).
- Any coach (or guardian; only athletes are blocked) who has the code calls `POST /api/groups
  {action:"join"}`. That adds them to `groups.coachIds` (`lib/group-actions.ts:96`) with no head-coach
  approval and no coach-seat limit, even though the invite path enforces both.
- They can now manage the group and read the full roster: emails and dates of birth, including minors'.
- If that coach then deletes their own account, `account/route.ts:30-45` deletes **the group, its
  memberships, check-ins, attendance and announcements**, because it cascades on `coachIds`.

*Fix, in this order:*
1. Account deletion cascades only `headCoachId` groups and `$pull`s from the rest (§1.5).
2. Return `code` only to that group's coaches.
3. A code-join by a coach either creates a pending request the head coach approves, or joins as a
   non-coach member; it also enforces `coachSeats`.

### High

**S4. Any logged-in user can read any group's roster (known).** `GET /api/groups?groupId=…`
(`app/api/groups/route.ts:110-227`) returns members' `email`, names and `dateOfBirth` with no membership
check. Re-verified. *Fix:* require that the caller is a member or coach of `groupId`.

**S5. Google OAuth links accounts on unverified emails (known).** `google/callback/route.ts:99-110`
auto-links Google to any existing password account with the same email and marks it verified, without
checking `verified_email`. *Fix:* reject unless `verified_email === true`.

**S6. Sentry receives PII and session cookies (known).** `sentry.server.config.ts:18` and
`sentry.edge.config.ts:19` set `sendDefaultPii: true`, which attaches request headers and cookies (the
`session` JWT) to server events. `tracesSampleRate: 1` also sends every request. The platform has under-13
users. *Fix:* `sendDefaultPii: false`, a `beforeSend` that strips `cookie` and `authorization`, and a
trace rate around 0.1.

**S7. The admin password is stored as the cookie value (known).** `app/api/admin/auth/route.ts:11-17`
compares the secret with non-constant-time `!==`, stores the raw `ADMIN_SECRET` as the cookie value, and
has no rate limit. `app/admin/layout.tsx:12` repeats the comparison. *Fix:* issue a signed admin JWT,
compare with `timingSafeEqual`, and rate-limit the endpoint.

### Medium
- **S8** Coaches can read and post comments on athletes' **private** logs. `comments/route.ts` checks
  "shares a group" but never `log.visibility` **(known)**. The rule exists in `buildVisibilityFilter`;
  reuse it.
- **S9** Log fields are not validated (type confusion, unbounded `notes`/`tags`, arbitrary `visibility`)
  **(known)**. Fixed by §1.3.
- **S10** Endpoints with no rate limit: `reset-password`, `verify-email`, invite `redeem`, `POST /api/groups`
  (join-code guessing), and `admin/auth`. Also, `lib/rate-limit.ts` silently disables all limiters if the
  Upstash env vars are missing in production **(partly known)**.
- **S11** `canManageGroup()` (`lib/api-auth.ts:17-18`) grants manage rights to any `role: "coach"` user
  who is merely a member, which widens S3 **(known)**.
- **S12** JWTs can't be revoked. A password reset (S1) or account deletion leaves existing 7-day sessions
  valid **(known)**. Cheapest fix: a `tokenVersion` on the user, checked in `getSession()`.

### Low
- `oauth_invite` cookie value is interpolated into a redirect path without `encodeURIComponent`
  (`google/callback/route.ts:159`). It stays on the same origin but is untidy.
- Minimum password length is 6 with no other policy. `TEST_ACCOUNT_EMAILS` in production would let anyone
  who registers one of those addresses skip verification and get the `club` plan; make sure it is unset in
  prod.
- `app/api/sentry-example-api` is an unauthenticated endpoint that always throws **(known)**. Delete it.

## 4. State & architecture health

1. **Membership has three writers' worth of truth and no owner.** `users.groupIds`, `groupMemberships`
   and `groups.coachIds` are written ad hoc from at least 8 call sites (group create/join/leave, members
   remove/transfer, coaches add/remove, 4 invite handlers, under-13 verification). `addUserToGroup()`
   exists, but most paths bypass it, so drift is guaranteed as features grow.
   *Direction:* one `lib/membership.ts` with `joinGroup` / `leaveGroup` / `promoteToCoach` /
   `removeFromGroup`, and a lint rule (or code review rule) that nothing else writes those fields.
2. **Business rules are duplicated, and the copies already disagree.** The legacy-visibility rule appears
   11 times in 3 files. "Do these two users share a group" is hand-rolled twice in `comments/route.ts`, and
   its omission of the visibility check is exactly bug S8. Extract `lib/log-visibility.ts` (§1.3) and a
   `canViewLog(db, viewer, log)` used by comments, reviews and the guardian calendar.
3. **Route boilerplate.** About 60 handlers repeat the same rate-limit, session, try/catch and error-shape
   code. `withApiRoute` (§1.3) removes roughly 900 lines and makes it impossible to forget the auth check.
4. **No schema layer.** Bodies are `Record<string, unknown>` cast with `as string`. This is the root cause
   of S1, S2, S9 and E6/E7. `zod` is installed but unused; adopting it per route as that route is touched
   is the highest-leverage change.
5. **Client data flow.** `app/dashboard/page.tsx` is the hub: 8 queries, 27-prop `DashboardFeed`,
   13-prop `DashboardSidebar`, filters and handlers drilled 3 levels. Mutations invalidate through
   `onMutateX` callbacks passed down as props, instead of components calling
   `queryClient.invalidateQueries` (or `useMutation`) next to the mutation. See §1.4.
6. **Two sources of truth for "active group".** The JWT claim, the DB field, the client `user` object, and
   the mirrored `useState` copy on the dashboard. The server mostly re-reads the DB (good), but
   `athlete/sync-group-schedule` trusts the JWT claim. Recommendation: treat the JWT as identity only
   (`userId`, `email`).
7. **Coupling to watch:** `lib/group-actions.ts` imports `createSession`, so a data helper writes cookies.
   That makes it unusable from scripts and jobs. Keep session issuance in the route layer.
8. **What's healthy:** centralized types (`types/dashboard.ts`), hierarchical React Query keys
   (`lib/query-keys.ts`), consistent `{ error }` shape, `safeObjectId` used on most path params, rate
   limiting on the hottest endpoints, and a good unit-test base for streak and date logic.
